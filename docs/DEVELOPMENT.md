# Development

The game runs under CrossOver, so nothing here launches it. `./verify` catches offline everything
that would stop the mod compiling, passing the loader's security check, or patching. What remains
is behaviour, and that needs the in-game checklist at the end.

## Layout

| Path | What |
|---|---|
| `mod/` | The shippable mod folder: `Manifest.json`, `Source/`, `Data Sheets/`, `Assets/`. `./deploy` copies exactly this. |
| `mod/Source/` | Raw C#. The game compiles it at load time. |
| `mod/Source/Core/<Area>/` | Pure logic. No UnityEngine, game or Harmony types allowed (enforced, see below). |
| `mod/Source/Game/<Area>/` | Adapters: Harmony patch classes (one target per class), actions, background tasks. |
| `mod/Data Sheets/*.DamageControl.xlsx` | **Generated** by `./build-sheets` from `data/`. Never edit by hand. |
| `mod/Assets/Icons/DamageControl/<area>/<Category>/<IconName>.png` | Raw PNG icons, served to the UI at runtime (see `docs/spec/WS0-API.md` §8). |
| `data/schema.json`, `data/<area>/*.json` | Data-sheet and locale row sources, one folder per workstream area. |
| `tools/SheetBuilder/` | Merges `data/` into the shipped workbooks (.NET 11 console app). |
| `tools/placeholder-icons/` | Stdlib Python script that draws placeholder icons. |
| `build/ModCompile.csproj` | MSBuild compile of `mod/Source` with the loader's references and options, for IDEs and fast feedback. |
| `build/generated/GameCompile.props` | Generated by `PatchVerifier refs`, git-ignored. |
| `tools/PatchVerifier/` | Offline compiler and verifier (.NET 11 console app). |
| `tests/DamageControl.Tests/` | xUnit tests over `mod/Source/Core` (linked source, current .NET). |
| `verify`, `deploy`, `build-sheets` | Entry-point scripts. Output is plain text with no colors. |

**Game path:** the Managed folder defaults to the Steam library path. To use another install, set
`UBOAT_MANAGED=/path/to/UBOAT_Data/Managed` in the environment, or pass
`-p:UboatManaged=...` to `dotnet build`.

## `./verify`

0. **Build data sheets:** `./build-sheets` validates `data/` and rewrites any changed
   `mod/Data Sheets/*.DamageControl.xlsx` (see "Data sheets and locales").
1. **Build the verifier.**
2. **Generate props:** `PatchVerifier refs` reads the loader model plus the game's `RoslynCSharpSettings`
   asset and writes `build/generated/GameCompile.props`. That file holds the references, `LangVersion`,
   defines, warning level, `Optimize` and `AllowUnsafeBlocks`.
3. **MSBuild compile:** `dotnet build build/ModCompile.csproj`. It uses no implicit framework references
   (`NoStdLib`, `DisableImplicitFrameworkReferences`), so the only references are the game's own
   `mscorlib`/`System`/… DLLs. Warnings are shown.
4. **Game-exact compile and verify:** `PatchVerifier all`.
   - Compiles with **Roslyn 2.10.0**, the same version the game ships, restored from NuGet. It uses the
     loader's exact options and writes `build/out/game/damage-control.dll`.
   - Compiles `Source/Core` alone against mscorlib, System and System.Core. This is the Core purity check.
   - Checks the manifest and the data-sheet containers.
   - Runs the game's own `Trivial.CodeSecurity` engine with the loader's restriction set.
   - Verifies the Harmony patches through `MetadataLoadContext`. No game code is executed.
   - Reads every mod workbook with the game's own `FastExcel.dll` and computes row paths the way
     `GameData` does. For our `Crew/Actions` rows, it checks that the type exists in the compiled mod,
     that it is a public, concrete `CharacterAction`, that it has both constructors, and that its contexts
     are valid. For our `General/Background Tasks` rows, it checks for `IBackgroundTask`, a public
     parameterless constructor, and `[Serializable]` when the event is `CampaignStart`. Every locale row
     must have English text. Rows that replace a base-game row are listed.
5. **Unit tests:** `dotnet test tests/DamageControl.Tests`.

The script exits non-zero if any step fails. The verifier exits 1 on errors; warnings are printed but do
not fail the run.

## What the loader actually does (2026.1)

These facts come from `UBOAT.Game.Core.Mods.Mod`/`ModManager`, the RoslynCSharp and Trivial.CodeSecurity
assemblies, and the serialized `RoslynCSharpSettings` object in `resources.assets`.

### Language: C# 7.0, not 7.3

The settings asset leaves `LanguageVersion` at `Default`, and Roslyn 2.10 maps `Default` to C# 7.0
(`Latest` would be 7.3). The following do **not** compile in game:
- C# 7.1: `default` literals, inferred tuple names, `async Main`.
- C# 7.2: `in`/`ref readonly`, `private protected`, non-trailing named arguments.
- C# 7.3: `==` on tuples, the `unmanaged`/`Enum`/`Delegate` generic constraints.

Both the MSBuild compile and the game-exact compile enforce this. Tests may use newer C#, but
`Core/*.cs` may not, because it is compiled for the game too.

### Defines

`UBOAT`, `UBOAT_2024_1` and `UNITY_STANDALONE_WIN`. There is no `UBOAT_2026_1`.

### References

The references are a fixed list: the anchor types in `Mod.Compile`, resolved to concrete DLLs in Managed
(see `LoaderModel` in the verifier). On top of that come the settings asset's extra references:
- `UnityEngine.dll`;
- the AI, Animation, AssetBundle, Audio, Core, ParticleSystem, Physics2D, Physics and UI modules.

`0Harmony` is referenced **only** when the manifest grants `Reflection`. There is no `netstandard.dll`,
and no `Unity.Collections`/`Unity.Burst`/`Unity.Jobs`. Any game API whose signature uses a type from an
unreferenced assembly fails with CS0012, both in game and here.

### Security check

The check is skipped on the launch that compiles the mod, and only runs on later launches. It runs when
the cached `Temp/<assemblyName>.dll` is loaded (`ScriptDomain.LoadAssembly`). A violation therefore looks
like this: the mod works once after an edit, then silently stops loading. `./verify` runs the real engine,
so this cannot surprise you.

The rules come from two places:
- **The settings asset:**
  - Denied members: `UnityEngine.Application.Quit` and `UnityEngine.Object.Instantiate`, which covers
    every overload and `GameObject.Instantiate`. Use the game's `ResourceManager.Instantiate`.
  - Denied type: `System.AppDomain`.
  - Denied assemblies: `UnityEditor` and `Mono.Cecil`.
- **`Mod.SetupSecurity`:**
  - Always denies the `System.Diagnostics` namespace. That rules out `Stopwatch`, `Debug.Assert` from
    System.Diagnostics and `Process`.
  - Without `IO`: denies `System.IO`.
  - Without `Reflection`: denies `System.Reflection`.
  - Without `Net`: denies `System.Net`.
  - Without `NativeAccess`: denies `System.Runtime.InteropServices` and unsafe code.

Namespace rules match the namespace **exactly**. `System.IO.*` blocks `System.IO` but not
`System.IO.Compression`. Do not rely on that gap.

The engine checks signatures, locals, fields and call, field and type operands. It does not check custom
attributes or `typeof`/`ldtoken`.

### Manifest

- **Reading:** `ModManager` reads `manifest.json` (matched case-insensitively on Windows) with
  `JsonUtility`. Unknown keys are ignored.
- **Permissions:** parsed with `Enum.TryParse(ignoreCase)`. A misspelt permission silently becomes
  "no permission", and the verifier treats that as an error.
- **`assemblyName`:** stripped to `[A-Za-z0-9 _-]` and must be unique. The compiled DLL is cached as
  `<persistentDataPath>/Temp/<assemblyName>.dll`. It is rebuilt when any source file, or the game's
  `com.uboat.game.dll`, is newer than the cache.
- **`supportedGameVersions`:** not checked by the loader. It is for the launcher only.

### Where things are loaded from

- **Code:** only `<mod>/Source/**/*.cs`. Prebuilt DLLs are ignored, and `Version X/Source` is never
  compiled.
- **Other content:** `Data Sheets/**/*.xlsx`, `Bundles/*` (top level only) and `Assets/**` (raw png, jpg,
  wav, ogg, aif). These load from the mod root and from compatible `Version X` / `Version X-Y` folders.

### Discovery and enabling

- **Local mods:** a local mod is `<persistentDataPath>/Mods/<folder>`, and its id is the folder name.
- **Enabling:** a mod is enabled when its id appears as a line in `<persistentDataPath>/modlist.txt`.
  Workshop ids look like `steam:<id>`.
- **Load order:** local mods are always loaded **before** Workshop mods, whatever order `modlist.txt`
  gives. Data-sheet rows are last-writer-wins, so a Workshop mod overrides our rows.

### Entry point

`UBOAT.Game.IUserMod`. The first implementing type found is created with `Activator.CreateInstance`, and
`OnLoaded()` runs after `[Inject]` static fields are filled.

## The patch verifier

### Patch registry

The mod's patch registry is its attribute-declared `[HarmonyPatch]` classes, applied by
`new Harmony(id).PatchAll()`. Patching through calls the verifier cannot follow is rejected:
- manual `Harmony.Patch` calls, `PatchProcessor` and reverse patches;
- `TargetMethod(s)`.

### Target resolution

Resolution mirrors Harmony 2.2.2 `PatchTools.GetOriginalMethod`:
- **Lookup:** targets are found with `AccessTools.Declared*`, so the member must be **declared** on the
  named type. An inherited method or property is an error, and the message names the type that declares it.
- **Overloads:** a name-only lookup that matches several overloads is an error (Harmony throws an
  AmbiguousMatch exception).
- **Supported method types:** `MethodType.Getter`/`Setter`/`Constructor`/`StaticConstructor` are
  supported. For `Enumerator`, the verifier checks only that the method exists.

### Patch method checks

- **Shape:** the method must be static. A prefix returns `void`/`bool`, a postfix returns `void` (or is a
  pass-through), and a finalizer returns `void`/`Exception`.
- **`__instance`:** not allowed on static targets, and the type must be compatible.
- **`__result`:** the target must be non-void, and the type must match. A prefix `__result` should be `ref`.
- **`___field`:** the field must exist on the type or a base type, with a matching type.
- **`__N`:** the index must be in range.
- **Named arguments:** the name and type must match a target parameter, and must be `ref` when the target
  parameter is by-ref.
- **Allowed injections:** `__state`, `__args`, `__originalMethod`, `__runOriginal`, and `__exception`
  (not in prefixes).

### Target flags

- **Errors:** Burst-compiled targets (a static `[BurstCompile]` method, or any member of a
  `[BurstCompile]` job struct), abstract or interface targets, and extern/InternalCall targets.
- **Warnings:** generic targets, members of job structs, `AggressiveInlining`, and non-virtual bodies of
  20 bytes of IL or less, which are at risk of being inlined by Mono.

### Other checks

- Exactly one concrete `IUserMod` with a public parameterless constructor.
- Every external type reference resolves in the game assemblies.

The C# compile already covers base types and overrides. Note that the verifier is stricter than Harmony
in one way: argument types must match exactly.

## Not verified offline

- **Gameplay:** runtime behaviour and gameplay effects. Harmony applying the patch at runtime is likely
  but not proven, since Mono JIT inlining decisions and MonoMod detours are only observable in game.
- **Data-sheet content:** row paths, our action and task types, contexts and English text are checked
  (above). Not checked: that the game *uses* a row the way we expect, such as wheel ordering, merge
  order against other mods, or parameter names read by game code.
- **Asset bundles and raw assets:** contents and keys.
- **Injection:** `[Inject]` fields being non-null at the time you use them.
- **Save/load:** serialization of `BackgroundTaskBase` state.
- **Other mods:** interactions, such as two mods patching the same method or overriding the same rows.
- **The settings parse:** the security rules are parsed from `resources.assets` by field layout. If a game
  update changes that layout, `PatchVerifier` stops with "implausible values" rather than guessing.

## Data sheets and locales

All data rows and locale rows come from `data/<area>/*.json`. The format is in `docs/spec/WS0-API.md`
§7. `./build-sheets` merges them into one workbook per game workbook, `General`, `Crew` and
`Locales`, named `<Workbook>.DamageControl.xlsx`. The game merges a mod file into the namespace
before the last dot of its name, and rows are last-writer-wins by path.

- **Schema.** Tables and their columns are declared in `data/schema.json` (WS0). Headers copy the game's
  own sheets.
- **Errors.** The build fails on unknown tables or columns, a row key in two files, a missing key,
  unknown contexts or start events, malformed `Name = value` parameters, a missing English text, a
  line break outside locale text, and any hand-made `.xlsx` in `mod/Data Sheets/`.
- **Format.** The output is deterministic, with fixed zip timestamps and stable order. Text is stored
  as inline strings: the game's FastExcel reader breaks on duplicate shared strings. Worksheets are
  `sheetN.xml` in workbook order, which that reader requires.
- **Committing.** Commit the regenerated `.xlsx` with its sources. `./build-sheets --check` fails on
  stale output.

## Deploy

`./deploy` runs `./verify` first; pass `--no-verify` to skip that. It then rsyncs `mod/` (dotfiles
excluded) to:

```
~/Library/Application Support/CrossOver/Bottles/Steam/drive_c/users/crossover/AppData/LocalLow/Deep Water Studio/UBOAT/Mods/damage-control/
```

- **Not touched:** it does not modify `modlist.txt`, the game install, or `Temp/`.
- **Enabling:** enable the mod once in the launcher's Mods tab, which writes the line `damage-control`
  to `modlist.txt`.
- **Timestamps:** unchanged files keep their timestamps and changed files get "now", so the game's
  recompile check fires.
- **Overrides:** `CROSSOVER_BOTTLE` and `MOD_ID` can be overridden in the environment.

## In-game smoke test checklist

The log is `.../LocalLow/Deep Water Studio/UBOAT/output_log.txt` in the bottle. Every mod line starts
with `[Damage Control] `. If a sheet edit does not show up, delete the game's parsed-sheet cache:
`.../UBOAT/Data Sheets/Damage Control - *.dat`. The game reuses that cache while its access time is newer
than the xlsx's.

### Load and patching

1. `./deploy`, then enable "Damage Control" in the launcher, accepting the Reflection permission if the
   launcher asks.
2. **First launch after a change (compile launch):**
   - no `error CS` lines for our files in the log;
   - `Temp/damage-control.dll` has a fresh timestamp;
   - the log contains `Damage Control 0.1.0 loaded; applying Harmony patches.` and then
     `Harmony patches applied.` with no Harmony exception between them;
   - `icons ready: 12 served` appears (WS0 placeholder icons; the count grows as workstreams add art);
   - no `bootstrap step ... failed` line.
3. **Quit and launch again (cached-DLL launch, security-checked):** the same `loaded` line appears. If it
   is missing, the security check rejected the cached assembly, which should not happen if `./verify`
   passed.
4. Check that there are no `NullReferenceException`s mentioning `DamageControl` in the log, including in
   the main menu, where gameplay singletons are null.

### WS0: registration, settings, icons

5. **Action registration (R10).** Start a new campaign and go aboard. Open the interaction wheel on
   the Workshop in the stern torpedo room. The wheel shows our three toggles after the workshop's own
   orders. The labels are "Enable hatch pressure blocking", "Stop sailors blocking leaks on their own"
   and "Stop the crew carrying the wounded on their own", each with its placeholder icon. Hovering
   shows the highlighted (amber) icon and the description. This proves the `LoadActions` postfix
   registered a mod type (04 §8 #15 as revised by D2). Set `General/Settings/Damage Control/Debug` to
   True to also see `action registration: 3 mod action rows registered`.
6. **Defaults (D3).** On a new campaign the log shows
   `campaign settings created: HatchPressureBlocking=False, AutoLeakBlocking=True, AutoCarryWounded=True`.
7. **Toggle.** Click a toggle with no crewman selected (NoCharacter), then again with a crewman selected
   (Normal). Each click flips the setting at once and logs `setting X is now on/off`. The label flips,
   no crewman walks, and no "work order" voice line plays (02 §6 #17, 01 §6 #23).
8. **Save/load (04 §8 #18).** Change all three toggles, save, quit to the menu and load. The log shows
   `campaign settings restored:` with the changed values, and the wheel labels match.
9. **Pre-mod save.** Disable the mod and load (or start and save) a campaign. Re-enable the mod and
   load that save. The log shows
   `this save has no Damage Control settings yet; creating them with defaults` and then
   `campaign settings created:` with the D3 values. Save, reload, and confirm `restored` this time.
10. **Removal.** Load a save made with the mod while the mod is disabled. Expect, at most, an error
    about the unknown task type; the campaign itself plays normally.
11. **Custom Actions coexistence (D2).** With the Custom Actions mod also enabled, each toggle appears
    exactly once on the Workshop.
12. **Boat layout.** With Debug on, going aboard logs `boat layout built:` with each hatch's lowY and
    highY. Check that the conning-tower hatch's lowY is near the control-room ceiling and the exterior
    hatch's lowY is near the top of the tower; this is the C12 replacement for 101.55 m and 102.8 m.
    A `boat layout unknown:` line means the dependent features stay off; report it.

### Per feature

13. For each new feature: exercise it, then save, quit, reload and confirm its state persists.
